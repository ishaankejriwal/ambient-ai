Can athenahealth's EHI export score the program integrity metrics a health system owns?

The framework spreadsheet lists 53 Program Integrity metrics. This page covers the 28 whose persona includes Provider or All. It writes each one as a formula in plain words, then shows which athenahealth FHIR EHI export resource and element supplies each piece of it. Pieces the export does not have are marked in red, with where to get them.

Of the 28 metrics, . Partly means the export has some of the inputs, usually the claims and the recorded outcomes, and an audit, a reviewer or a vendor supplies the rest.

The same 28 cards exist for Epic and Oracle Health. The formula and the variables are the same on all three pages, and only the sources change.

Resource, record and element

Resource
One file in the export, like one tab of a spreadsheet. The Epic and Oracle pages call this a table. Payment is the file of payments posted to visits.
Record
One JSON object in that file, like a spreadsheet row. In Payment one record is one payment entry on a visit. In Claim one record is one electronic claim.
Element
One named value in a record, like a spreadsheet column. Payment.insurancePayment.value is the amount the insurer paid. Nested names are joined with dots.

Most formulas count records, so each card says what one record stands for in every resource it uses, and each chip in a formula repeats it.

The box around a variable shows where it stands. Visits is in the export. Note time is partly there: the export has a stand-in or part of the answer, and the rest comes from somewhere else. Survey score is not in the export.

The status beside each metric's name follows from those boxes. Yes means every variable is in the export. Partly means some are, or the export has a stand-in. No means none are. Some cards end the In athena part with "Also in the export". Those are elements that help but sit outside the formula, and they do not change the status.

Every rate and percent change comes out as a fraction. 0.05 is 5 percent, or 5 percentage points when it is the gap between two rates. Count each case once. If the bottom of a fraction is zero, report N/A.

How to read the athena docs

  • Each resource has a profile page (StructureDefinition-athena-<name>-profile) listing its elements and allowed codes, and a Mappings tab naming the athenaPractice or athenaFlow table and column each element comes from. The Mappings tab is the place to settle what a field means.
  • Every chart document becomes an Encounter. The Encounter page says each physician interaction results in a chart document, and the resource is built from the DOCUMENT table. So phone notes, refill notes and result notes are Encounters too, and some athenaPractice visits also produce a second Encounter from the PatientVisit table. Keep visit document types only (Encounter.type:DOCTYPE) or require an Encounter.appointment, and count appointments rather than Encounters where you can.
  • DocumentReference.context.encounter points at the Encounter built from the same DOCUMENT row. DocumentReference.authenticator and Encounter.extension:AUTHENTICATOR are both the document's signer. The extension's slice is misspelled "AUNTHENTICATOR" on the profile page, so match it by its URL.
  • Documents are versioned. docStatus is preliminary, final, amended or entered-in-error. In base FHIR an amendment is a new record whose relatesTo.code is "replaces" and whose target becomes "superseded", and an addendum is a new record with "appends". The athena pages map these from internal codes without saying how, so verify on one known amended note and one known addendum. Drop entered-in-error records everywhere.
  • Note text is an attachment under DocumentReference.content. The mappings build every attachment as a Binary record, so expect to fetch Binary rather than find inline text.
  • Two timestamps matter and only one is explained. DocumentReference.date comes from the DOCUMENT row's WHENCREATED column, the time that version was created. DocumentReference.extension:pubtime comes from its PUBTIME column, and the docs do not say whether that is the signing time or a filing time. Check it against a few notes whose history you know before using it as the sign time.
  • References are IDs. DocumentReference.authenticator points at a Practitioner record, which has the name and NPI (the national provider identifier). Practitioner records come from different source tables for clinical and billing data, so one clinician may have two IDs. Join on NPI when crossing from notes to charges.
  • The export is requested per group (Group $export): all patients, the patients whose responsible provider is one practitioner, or the patients whose home location is one site. Use the all-patients group, since a provider's visits include other providers' panel patients. The date filter (_since) returns only records changed after a date, so the before period needs a full pull.
  • Billing resources (Charge, Claim, Payment) exist only for athenaPractice. athenaFlow sites have no charges in the export. Charge is a custom logical model, not a standard FHIR resource.

The resources that matter here

  • The billing resources are exported only for athenaPractice. athenaFlow sites have none, so their billing cards need the billing system they use.
  • Charge: one record per charge line, with the CPT code, units, copay and auth number. It has no contract rate and no void or status element.
  • Payment and Deductible: amounts posted to a service on a visit, tied to the visit by ticketNumber. Neither has a claim number, a denial code or an adjustment reason.
  • Claim: one record per electronic claim, with the insurer, who filed it, the day it was sent and the claim file text in claimData. It has no visit ticket and no payer decision.
  • The EHI export has no audit log. AuditEvent has a profile page but is not on the export's list of resources.

Where the AI shows up

  • athena documents no AI or automation marker on any resource. Get the tool's case log from the vendor, with the patient, service date and insurer for each case so you can match it to the export.
  • Ask the vendor whether its tool files claims in athena under its own user. If it does, look for that user in Claim.filedBy.

Words every card uses

AI case
A claim, visit or request the AI handled, taken from the vendor's log and matched to the export by patient, service date and insurer.
Before, After
Fixed periods before and after the AI went live.
Ticket
athenaPractice's number for one visit, ticketNumber on Charge, Payment and Deductible. Payment has no claim number, so one ticket and one insurer stand in for a claim.
835 remittance file
The electronic file a payer sends back saying what it paid, adjusted or denied on each claim line. The export does not include it.

Inputs outside the export

  • Denials, remittance detail, claim numbers on payments and appeal outcomes. Get them from the 835 remittance files and the payers' letters.
  • Prior auth requests, with the time sent, the urgency and the decision.
  • Confirmed audit findings, coder reviews and contract rates.
  • The AI's own log: what it flagged, suggested, read and handed to a person, with a full audit trail.
  • Program costs, and provider demographics such as race or ownership status.
