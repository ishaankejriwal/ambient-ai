Can Epic's EHI export score the program integrity metrics a health system owns?

The framework spreadsheet lists 53 Program Integrity metrics. This page covers the 28 whose persona includes Provider or All. It writes each one as a formula in plain words, then shows which Epic EHI export table and column supplies each piece of it. Pieces Epic does not have are marked in red, with where to get them.

Of the 28 metrics, . Partly means Epic has some of the inputs, usually the claims and the recorded outcomes, and an audit, a reviewer or a vendor supplies the rest.

The same 28 cards exist for Oracle Health and athenahealth. The formula and the variables are the same on all three pages, and only the tables and columns change.

The box around a variable shows where it stands. Visits is in the export. Note time is partly there: the export has a stand-in or part of the answer, and the rest comes from somewhere else. Survey score is not in the export.

The status beside each metric's name follows from those boxes. Yes means every variable is in the export. Partly means some are, or the export has a stand-in. No means none are. Some cards end the In Epic part with "Also in the export". Those are columns that help but sit outside the formula, and they do not change the status.

Every rate and percent change comes out as a fraction. 0.05 is 5 percent, or 5 percentage points when it is the gap between two rates. Count each case once. If the bottom of a fraction is zero, report N/A.

How to read the Epic site

The Epic EHI table index lists the export schema. Each table page describes its primary key and columns. Run calculations on your organization's exported files after checking its Epic version and local configuration.

  • Columns ending in _C_NAME are pick-lists. The page lists the allowed values, and sites can add their own.
  • Most provider, payer, procedure and diagnosis IDs come out as names. You get PAYOR_ID_PAYOR_NAME, not PAYOR_ID. Patient, visit, account, claim, denial, DRG, remit code, rule and user IDs are real IDs.
  • The diagnosis master CLARITY_EDG exports names only, no ICD-10 codes. The codes as billed are in CLM_DX (diagnoses) and CLM_PX (ICD procedures). The CPT code as billed is in INV_CLM_LN_ADDL (professional) and HSP_ACCT_CPT_CODES (hospital).
  • DATETIME (UTC) and DATETIME (Local) are real timestamps. For plain DATETIME, check the column description before assuming it contains a time of day.

The tables that matter here

Epic bills in two systems, so most metrics have two versions. Hospital billing (HB) is one hospital account per stay or visit, with claims, denials and coding attached to it. Professional billing (PB) is one charge per service, grouped into invoices, which are the claims.

  • Claims. HB: HSP_CLAIM_DETAIL2 and HSP_CLAIM_DETAIL3, one row per claim sent. PB: INV_BASIC_INFO, one row per invoice sent, and INV_CLM_LN_ADDL, one row per claim line with the code, paid amount and denial code.
  • Denials. BDC_INFO, one row per denial, underpayment, overpayment or payer letter, including RAC and ADR record requests. HSP_BDC_DENIAL_DATA adds the dollar amounts per line. Epic built ARPB_PMT_RELATED_DENIALS for denial rate reporting. It links PB payments to their denials and already drops duplicate-claim denials.
  • Remittances. CL_RMT_CLM_INFO and CL_RMT_CLM_ADJ, the 835 file as received, with the claim status and the adjustment reason codes.
  • Money. HSP_TRANSACTIONS (HB) and ARPB_TRANSACTIONS (PB), one row per charge, payment or adjustment. Refunds are in HSP_ACCT_RFND_TX and ARPB_TX_REFUND.
  • Coding. HSP_ACCT_DX_LIST, HSP_ACCT_PX_LIST and HSP_ACCT_CPT_CODES, the final coded set per hospital account. HSP_ACCT_CDSTS_HX is the coding status history. CODING_CLA_NOTES is one row per coding or CDI query sent to a physician.
  • Prior auth. REFERRAL, one row per referral or auth request, with REFERRAL_HIST for every status change and AUTHORIZATIONS for the service-level auth status.
  • Who did what. HSP_BFH_ACTIVITY, one row per billing action with the user and whether it was a person or the system. CLM_VAL_AUDIT_TRAIL, one row per hand edit to a claim.

Where AI and automation show up

  • CODING_CLA_NOTES.QRY_IS_AI_SUGG_YN. A coding or CDI query was suggested by AI. The reason, the evidence it cited and the reason a user rejected it are in the same table and in CODING_CLA_NOTES_EVIDENCE.
  • CLAIM_SCRB_RESULT.CLM_SCRB_ATFIX_YN. A claim scrubber edit was fixed automatically, with no person involved.
  • HSP_ACCT_CDSTS_HX.CDSTS_HX_SVC_STS_C_NAME. Epic's automatic simple visit coding succeeded or failed on the account.
  • FAC_CHG_AI_RUN_INFO. One row per run of the facility charge calculator's AI on an ED visit, so count distinct visits. FAC_CHG_OVERRIDE has the score and the score a user typed over it, and FCC_SCORE_AUDIT has every change with user and time.
  • V_EHI_AUDIT_HAR, V_EHI_AUDIT_CLP and the other V_EHI_AUDIT_ views. One row per change to a hospital account, claim or other record, for the columns Epic configured for export, with old value, new value, user and time.
  • BDC_INFO.APPEAL_LLM_TEXT_GENERATED_YN = 1. Epic's LLM drafted the appeal for this denial. 0 means it tried and failed.
  • AI_INTRCT_INFO, AI_SESSION_HX, AI_INTRCT_REASON. Epic's own LLM sessions: user, patient, status history, and the model's stated reason.
  • HSP_BFH_ACTIVITY.ACT_SOURCE_C_NAME. Whether a billing action was done by staff, the system or the patient.

These are the billing-side traces. Other Epic AI features (surgery scheduling, patient messaging) log elsewhere. A vendor tool that works outside Epic leaves none of these traces. Its only sign in Epic is a service account in a user column, so ask the vendor which user ID it writes under. Tables starting with AUTH_REQUEST, UM_AI_, APPEAL_GRV and CLAIM_INVOICE belong to Epic's payer product (Tapestry). They are empty unless the health system also runs a health plan, so this page does not use them.
